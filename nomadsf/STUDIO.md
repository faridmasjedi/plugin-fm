# NomadSF Studio

A Salesforce developer workbench in the spirit of the Developer Console and Salesforce Inspector Reloaded. One UI, several places to run it:

| Where                                            | How it reaches Salesforce                                                                  | Status  |
| ------------------------------------------------ | ------------------------------------------------------------------------------------------ | ------- |
| **NomadSF app** — `sf fm dashboard` → **Studio** | through the local server with the Salesforce CLI's login; the token never reaches the page | ✅      |
| **Browser extension** (Chrome, Edge)             | the browser's own Salesforce session (`sid` cookie of the org you are on) — no CLI needed  | ✅      |
| **VS Code extension**                            | webview, CLI login through the extension host                                              | planned |
| **Desktop app** (Electron)                       | CLI login through the main process                                                         | planned |

## Features

- **Settings** — **AI** (extension): connect your own AI without the CLI app — Anthropic Claude, OpenAI, Gemini, Mistral, Groq, OpenRouter (key or **Sign in with OpenRouter**), GitHub Models, Ollama on this computer, or any OpenAI-format endpoint (your model or a company gateway); choose the model, **Connect and test**, **Disconnect**. The key is kept in the extension's own storage (`chrome.storage.local`; websites cannot read it) and sent only to that provider; Chrome is asked for access to that provider's address only when you connect it. The ✦ buttons then use it: Query (Write SOQL), Execute Apex (Write Apex; Explain this error → Use the fixed code), REST Explorer (Build the request; Explain this response), Code (✦ Describe a new class → editable draft → Create this class; Explain, Review, Write test class → Create this test class; Explain compile errors → Use the fixed code), Debug Logs and Apex tests (Explain). AI only fills editors or shows text: nothing runs or saves until you press the usual button (with the usual org-name check); without it they use the CLI app's AI when that runs. **Org**: in the extension, every org you are logged in to in this browser (its own Salesforce login: no CLI, nothing stored), with name, type (production, developer, sandbox, scratch) and whether the login still works; **Use** switches the Studio, **Log in to … ↗** opens the Salesforce login to add one (it appears when you come back). The header becomes an org dropdown when there are several. In the app: the Salesforce CLI's orgs. **Project**: choose the Salesforce project once and every page uses it: the NomadSF app's own project (in the app), a folder on this computer (read-only, nothing uploaded) or any GitHub repository and branch. In the extension, also **Use the NomadSF CLI app on this computer** (off by default, so the extension never contacts it) and its port.
- **Project** — a dashboard of the chosen project (with **Change** to go to Settings), in two tabs. **Overview**: components, package directories, manifests, API version and branch; click a type for its components or **Add all to package**; click a manifest to load it into Metadata. **Compare with the org**: tick the metadata types (or All) and compare them in one table (in both / only in org / only in project; components of installed packages and other namespaces are left out). **Check content** splits code in both (Apex, Visualforce, LWC, Aura) into different / same (other metadata types are not compared yet). Tick rows, then:
  - **Restore into project** (only in org): retrieves them into the project on this computer (needs the NomadSF CLI app).
  - **Download zip** of what is in the org.
  - **Delete from org** (only in org): a destructive deploy run from the browser, so it works in the extension too.
  - **Open in Code** (one code row): the Code page with the org and project versions side by side.
  - **Deploy to org** (in the project): code (Apex, Visualforce, LWC, Aura) deploys straight from the project in the browser, so it works in the extension with a folder or a GitHub branch; other metadata uses `sf project deploy start` through the CLI app.
  - Delete and Deploy choose the tests (no tests in sandboxes only, specific classes, all local, all in org) and **Validate only** (on by default); a successful validation offers **Quick deploy**. Component and test failures are listed; everything asks for the org name and goes to Activity.
- **Execute Anonymous** — Monaco editor with Apex highlighting and snippets (`debug`, `query`, `for`, `try`, `limits`), log level presets, run all (⌘/Ctrl+Enter) or the selection (⌘/Ctrl+Shift+Enter), compile errors marked on the line, history of the last 20 snippets.
- **Code** — the Developer Console editor for every kind of source code the Tooling API can edit: Apex classes, triggers, Visualforce pages and components, LWC and Aura bundles (filterable lists; Monaco with Apex / JavaScript / HTML / CSS / XML colouring). **Check** compiles without saving; **Save** compiles and saves Apex and Visualforce (MetadataContainer, like the Developer Console) with problems marked on the line; LWC and Aura files save one by one (unsaved files marked •). **New …** creates any of them from a starter template (a trigger asks for its object; an LWC gets its .js and .html, Aura its .cmp and controller). Every create and save asks for the org name and goes to Activity. In production Salesforce only accepts Apex and Visualforce through a deployment, so their Save and New are off there (Developer Edition orgs allow them). **With a project open** (folder, GitHub branch or the app's project) the list also shows what is only in the project, and tags each item: ≠ different, = same, org / project when only on one side; **Check content** compares all of a kind at once, and a filter shows only the different ones (or only in org / only in project). Opening an item gives three views: **Org** (the editor), **Project** (read-only) and **Compare** (side by side, changed lines highlighted, ↑ ↓ between changes, ignore spaces, inline); LWC and Aura bundles file by file (● different, + only in the project, − only in the org). **Use project version** loads the project's code into the editor as unsaved changes (Check / Save as usual, Compare then shows no differences); **Deploy from project…** deploys a component that is only in the project, or a bundle with new files (no tests: sandboxes and developer orgs; production goes through Project → Compare with tests); **✦ Explain the difference** sends the diff of the file, not the whole file, to the AI. Configuration metadata (flows, objects, layouts…) is XML, not code: use the Metadata page for it.
- **Apex tests** — finds the org's test classes, runs the selected ones or all local tests (asynchronously, with progress), failures first with message and stack trace. **Code coverage**: org-wide percentage against the 75 % production rule, every class and trigger by coverage, and the source with covered lines green and uncovered red.
- **Debug Logs** — turn debug logging on for yourself for 30 min / 1 h (trace flag with a `NomadSF` debug level, extended if one is active), list logs (only mine / everyone, auto-refresh), open, download, delete.
- **Log viewer** — Debug messages, every event (filter by type), governor limits with usage bars, raw log; SOQL / DML / error counts.
- **Query** — SOQL editor with autocomplete of objects (after `FROM`) and fields of the main object (also with subqueries), Tooling API, deleted & archived rows, up to 50,000 rows, "All fields", history, **saved queries** (named; click to load, × to delete; Export / Import as `nomadsf-queries.json`, or **From project** to load the team's file from the repository root); results in a sortable table with per-column filters (`=exact`, `!not`, `>10`, `<5`), record links, Copy / CSV / JSON.
- **Record** — Salesforce Inspector's "Show all data": paste an Id, a record URL or a username; every field with label, API name, type and value; filter, only filled fields, follow lookups, recent records. **Edit** changes fields inline (picklists and checkboxes as such); only changed fields are saved, after you type the org name. Users: **Log in as this user**. Every Id in a result table has an ⓘ that opens it here, and the extension popup offers **Show all data of this record** on a record page.
- **Org compare** — differences between two orgs (sandbox ↔ sandbox, or sandbox ↔ production; any two orgs you are logged in to): pick a source and a target and the metadata types (All / Common), **Compare** lists only in source / only in target / in both (installed-package and other-namespace components left out); **Check content** retrieves the components in both orgs and marks them different or same (line endings and XML whitespace ignored). **Select the difference** (only in source + different), optionally **also delete** what exists only in the target, then **Build package**: download `package.xml`, `destructiveChangesPost.xml` and a deployable **zip** (metadata format, only the chosen components) to use later (here, Workbench, or `sf project deploy start --metadata-dir`), or **Validate / Deploy** it on the target with the test level you choose and **Quick deploy** after a validation (org name asked; logged on Activity).
- **Backup** — data backups saved as jobs, in three tabs (**What to back up**, **Schedule & folder**, **Backups & restore**) under a header with the job's summary, **Back up now** and the progress. **What**: objects you pick, or all custom / all standard / all objects (new ones join automatically; untick any to leave out); sharing rows, history, feeds, events and custom metadata are not offered. Per object a SOQL **condition** (which records) and the **fields**: all, only these, or all except these (Id and SystemModstamp always kept; address and file-body fields cannot go through the bulk API). **Count records** before running. **Where**: a folder on this computer (chosen once; Chrome asks once to allow writing), or **Download as zip** for small backups. Each run is a folder `<job>/<time>/` with one folder of CSV files per object (50,000 rows per file), `manifest.json` (org, kind, row counts, errors, and the field definitions at that moment for restoring later) and `backups.json` listing the runs. **Incremental**: after a full run only records changed since the last run, plus `deleted.csv` with the Ids deleted since (recycle bin), and a full run again every N days. **Files and attachments** (Settings): the Salesforce Files linked to the backed-up records (latest version, and who each file is shared with) and their classic attachments go into the run's `_files` folder, up to a size per file (larger ones listed as skipped); incremental runs add files changed since. **Encryption** (Settings): a passphrase encrypts every data file and file of the backup in the browser (AES-256-GCM, key from PBKDF2-SHA256; only the list of runs stays readable); the key can be kept on this computer (needed for scheduled runs; kept as a key that cannot be read back) or asked for each session (an **Unlock** bar appears); a wrong passphrase is refused; without it nobody can read the data, and it cannot be changed or recovered. **When**: now, daily or weekly at a time; scheduled backups run while NomadSF is open in Chrome (a missed run happens once when you open it; the extension icon shows a badge when one is due). One object failing does not stop the others; it is shown in the run. **Backups in the folder**: the runs, what each holds, and the records of any object. Backing up only reads the org. **Restore** (on an opened run, into the job's org), for **one or more objects** at once: the records as they were at that run (its last full run plus the incremental runs up to it), **Compare with the org**: changed values (backup vs now) and records deleted since (still in the recycle bin or not). Tick values → **Put back** (empty in the backup clears the field; lookups to records created again by an earlier restore use their new Ids). Tick deleted records → **Bring back**, keeping relationships: with **Bring back the deleted records they point to** (on) a deleted Case's Account (and that Account's parent…) comes back too when it is deleted as well; recycle-bin records are undeleted with their Ids; the others are created again with new Ids, lookups between them rebuilt, and records still in the org that pointed to them and lost the link are pointed to the new ones (a link changed since the backup is left alone). **With their files and attachments**: the files and attachments of the records created again are uploaded from the backup and linked to them (a file still in the org, linked to another record, is linked again rather than uploaded twice). Backup Id → new Id is kept in the folder (`restored-ids.json`) for later restores and comparisons, and downloads as a CSV. **Keep the old Ids in the org** loads the records created again through `NomadSF_Old_Id__c` (see Migrate). Everything asks for the org name and goes to Activity. **Copy into another org…** opens Migrate with the run as the source.
- **Migrate** — in three numbered steps (from and into, what to copy, check and copy): copy records from one org into another (any two you are logged in to), or from a backup run. Tick objects in any order: NomadSF loads parents first (lookups between the copied objects decide the order; lookups to the same object, or across a circle, are set in a second pass). Per object a condition, a field choice, and **related only**: just the records that point to records of the objects loaded before it, to seed a sandbox with e.g. 100 Accounts and their Contacts and Opportunities. **Children…** on a chosen object lists the objects that point to it (Contacts, Cases, Opportunities of Accounts, custom objects…) with how many records each would bring for the chosen parent records (its condition applied); **Tick those with records** and **Add as Related only** add them in one click. **Mask personal data** (on by default from production into a sandbox): e-mails, phones, people's names and streets become stable fake values (the same value always gets the same fake one); any masked field can be unmasked. **Check plan** shows the steps, records per object, fields that do not exist in the target, lookups set afterwards and masked fields; owners are matched by username (sandbox suffix ignored, others get you as owner), record types and queues by API name. **Relationships are kept**: with **Bring the records they point to** (on by default) every record a copied record points to is copied too, up the chain (a Case's Account, that Account's parent…), even when a condition left it out. **Links between records** lists every lookup before copying: how many point to a copied record, to a record already in the target, or would be empty, with a fix per lookup: bring the parents, link to records already in the target with the **same Id** (sandboxes refreshed from the same production) or the **same Name / external Id / unique field**, or **copy only the records pointed to** (an object's records choice: All / Related only / Only those pointed to). Changing a fix marks the plan to check again before copying. Copies from the same source org (chosen directly or through a backup) share their Id map, so Cases copied after their Accounts still link to them. **Copy files and attachments** (up to N MB each, max 35 for a browser upload): after the records, their Salesforce Files are uploaded and linked to the new records (shared files linked to every copied record they were shared with) and attachments re-attached; the plan counts them and their size; a re-run skips what was copied. **Large copies**: batches go 4 at a time, the Id map is saved every few thousand records (an interrupted copy, run again, updates instead of duplicating), Bulk loads are split into jobs of 10,000 rows, and the plan warns when the target's data or file storage or today's API calls would not be enough, and suggests the Bulk mode below for more than 50,000 records. **Keep the old Ids in the target org** (off by default): before the copy NomadSF creates a field `NomadSF_Old_Id__c` (text 18, External ID, unique) on each object being loaded and a permission set `NomadSF_Old_Ids` assigned to you (shown in the plan and in the confirmation; a metadata change, so it needs the right to customize the org). Records are then upserted on that field with the Bulk API (large volumes, re-runs never duplicate, and every record shows the Id it had in the source); old Id → new Id is read back from the org after each object, so lookups point to the right records. Objects that cannot have custom fields use the in-browser Id map. **Remove the old-Id fields…** deletes the fields (and their values) and the permission set when the data is final. **Copy** asks for the target org name (red for production); records go through the REST collections API (200 per call) so every new Id is known. Results per object with failures (downloadable); a second copy **updates** what the first one created instead of duplicating; **Undo last copy** deletes what it created, children first.
- **Choosing objects** (Backup and Migrate) — three tabs: **Browse** (filter, only chosen, a table of label / API name / tags such as where, fields and record counts, with Settings per object), **Type names** (API names or labels separated by commas, semicolons or new lines; names that do not exist are listed, not added; add to or replace the choice) and **✦ Describe** (with an AI connected: say what you need in words, e.g. "50 customer accounts with their contacts and open opportunities"; the AI picks objects, conditions, fields and related only from this org's object list, unknown names are listed, and the choice is shown for review; nothing runs until the usual button). After a copy, **✦ Explain these failures** groups the failed records by cause with fixes.
- **Field usage** — choose the object (custom fields only, or all); click a field for two tabs. **Usage**: count its filled values and see which components use it (custom fields). **Access**: every profile, permission set and permission set group with Read & edit / Read only / No access; click a tile to list that level and filter by kind (repeated names show their licence). **Count all** counts every field in the list.
- **Events** — listen to Platform Events, Change Data Capture (all changes or per object) and PushTopics live, new events only or replaying the last 72 hours; payload of each event; publish a platform event from JSON (asks for the org name). In the app the stream goes through the local app (which keeps Salesforce's streaming cookie); in the extension it uses the browser session.
- **Org limits** — every limit of `/limits` with used, max and a usage bar, most used first.
- **REST Explorer** — any `/services/` call (`vXX.X` = latest version) with formatted JSON, timing and API usage; links in the answer are clickable. POST / PATCH / PUT / DELETE ask for the org name and go to Activity.
- **Names for Ids** (Query, off by default) — tick it to add name columns next to Id columns SOQL cannot follow, e.g. `LoginHistory.UserId → Name` and `→ Username`, or a polymorphic `WhoId → Name`. Read-only: one extra query per 200 different Ids (at most 20,000 per result); the names are shown and exported with loaded rows, not in Bulk API exports.
- **Data (Bulk API 2.0)** — two tabs. **From a CSV file**: upload, edit the rows in a grid, check which columns Salesforce accepts, then insert / update / upsert / delete / hard delete only the ticked rows. **From a query**: load records with SOQL (with Id, up to 10,000), edit cells in place (formula, system and related fields are locked 🔒), **Update** sends only the changed fields of the changed records (a cleared cell empties the field), **Undo changes**, tick rows to **Delete** them; plus delete every record a query returns. Export lives on the Query page.
- **Lookup** — "VLOOKUP against Salesforce": upload a CSV, pick a column, and look its values up in any object. Ids are recognised by their prefix (e.g. ProfileId → Profile); other values are matched on a field you choose (User by Username, Contact by Email, an External Id…). Pick the fields to bring back (or all), plus related fields such as `UserLicense.Name`. You get your file back with `Column → Field` columns and a Found column (yes / no / several), and the records found; both export to CSV. Read-only, 200 values per query, the number of API calls shown before running (asks above 50). CSV only for now (Excel: Save as CSV).
- **Users & access** — five tabs. **Login history** (1–180 days, with usernames) and **Setup audit trail** (7–180 days). **Permission sets & groups**: see assignees, remove selected, assign by usernames, profile, role or public group, with an optional expiry. **Object, field & system permissions**: pick a profile, permission set or group and see its object access (read, create, edit, delete, view all, modify all), field access (per object) and user & system permissions (granted only, or all). **Users**: find a user by name, username, email or Id, then edit any field inline (typed org name), **Freeze / Unfreeze**, **Activate / Deactivate** and **Log in as**.
- **Metadata** — every metadata type of the org; list components (folder types such as reports and dashboards folder by folder), build a package that mixes types, then **Download zip** (Metadata API retrieve), **package.xml** (download / copy), or in the app **Retrieve into project** (`sf project retrieve start`).
- **Local app (extension)** — when `sf fm dashboard` runs on this machine, the extension also shows its CLI orgs and AI settings, plus E2E tests and the ✦ AI buttons; without it they are hidden. Release runs, runbooks and the repository stay in the NomadSF release app (`sf fm dashboard`). Port configurable (default 7007).
- **Tests** — Playwright scenarios of the project, run through the local app (`sf fm e2e run`), last results and the HTML report.
- **AI help** (✦, with the AI connected on the local app's AI page; keys stay in the app):
  - **Query → Write SOQL** from a plain-English question, using the org's own objects and the fields of the objects you mention.
  - **Explain with AI** on any debug log (errors, limits, likely fix; long logs are cut down to the telling lines first).
  - **Explain failures with AI** for failed Apex tests.
  - In the app: **Explain with AI** on a failed pipeline stage, and **Draft release notes** on Repository (commits and changed files since the last deployment tag).
  - Every answer shows the provider, the model and how much was sent.
- **Activity** — every export and change made with the Studio, kept in this browser.
- **Access hints** — errors that usually mean the user lacks access (insufficient access, an object or field the user cannot see, API not enabled, feature off) get a plain-language line; empty results (queries, login history, audit trail, permissions, field access) say the user may not be able to see the records.
- **Safety** — production orgs (including Dev Hubs) are shown in red, and running Apex or turning on logging there asks first. Every data or access change asks you to type the org name, in any org.

## Run it

```bash
# From the plugin repository
yarn build:studio              # builds nomadsf/ and copies the Studio into dashboard/studio
sf fm dashboard --open         # NomadSF → Studio ↗  (http://127.0.0.1:7007/studio/)
```

### Browser extension

```bash
cd nomadsf && yarn install && yarn build
```

- Chrome / Edge → `chrome://extensions` → Developer mode → **Load unpacked** → `nomadsf/apps/extension/dist`.
- Open any Salesforce page (Lightning, Setup, Classic) and click the NomadSF icon, or the small **N** tab on the right edge of the page (Alt+Shift+N).
- `nomadsf/apps/extension/nomadsf-extension-<version>.zip` is the package for the Chrome Web Store / Edge Add-ons. Every GitHub release has it attached.

The extension asks for `cookies`, access to `127.0.0.1` / `localhost` (the local NomadSF app) and to Salesforce domains only (`*.salesforce.com`, `*.force.com`, `*.salesforce-setup.com`, `*.cloudforce.com`, `*.site.com`). It reads the `sid` cookie of the org you are on and calls the Salesforce API with it, like Salesforce Inspector does. Nothing is sent anywhere else.

### VS Code

`nomadsf-vscode.vsix` (from a release or the `extension-latest` pre-release; or `yarn --cwd nomadsf/apps/vscode package`): **Extensions → … → Install from VSIX**. Needs the Salesforce CLI with plugin-fm.

- Opening a Salesforce DX project starts the local app for that workspace (or switches a running one to it), and **NomadSF** in the status bar opens the Studio in an editor tab. Everything of the app and the Studio is there: runs and approvals, orgs, runbooks, AI, and every Studio page.
- Commands (⇧⌘P → NomadSF): _Open the app_, _Open Studio_, _Open Studio page…_, _Stop the local app_. In the editor (right-click on a selection): **Show all data of the selected record Id** and **Run the selected SOQL in Studio**.
- Settings: `nomadsf.port` (7007), `nomadsf.sfCommand` (`sf`), `nomadsf.autoStart`. Works in remote windows and Codespaces (the port is forwarded).

### Desktop app

`nomadsf/apps/desktop` (Electron, kept out of the yarn workspaces so normal installs do not download Electron):

```bash
cd nomadsf/apps/desktop && npm install
npm start          # choose a Salesforce project folder; the app opens in its own window
npm run dist       # installers: dmg / zip (macOS), NSIS (Windows), AppImage (Linux)
```

It starts `sf fm dashboard` for the project on a free port, finds `sf` through your login shell's PATH (also when started from the Dock), remembers the last project (**File → Open Salesforce project…**, ⌘O to switch), and has **Go → Runs / Studio / Orgs / AI**. Only the local app opens inside the window; sign-ins and Salesforce links open in your browser. Quitting stops the local app.

## Develop

```
nomadsf/
  packages/core       Salesforce client (fetch + transports), SOAP execute anonymous, query, logs, trace flags, log parser
  packages/ui         Studio (React, Vite, Monaco bundled locally — no CDN, required for MV3)
  apps/extension      popup, background service worker, floating button, manifest + icons + store zip
```

```bash
yarn test        # core unit tests (vitest)
yarn typecheck
yarn --cwd packages/ui dev   # Studio with hot reload; /api is proxied to a running `sf fm dashboard`
```

The core talks to Salesforce through a **transport**: `proxyTransport` (NomadSF app: the local server adds the token), `fetchTransport` (extension: session id). VS Code and the desktop app will add their own transport, so the core and the UI stay the same everywhere.
