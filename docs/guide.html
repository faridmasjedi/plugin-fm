NomadSF Guide

NomadSF Studio is a Salesforce workbench in the spirit of the Developer Console and Salesforce Inspector, with data protection tools on top. This guide takes you from installing it to backing up, restoring and moving data.

Install

Chrome or Edge

  1. Download nomadsf-extension.zip from the latest release and unzip it.
  2. Open chrome://extensions (Edge: edge://extensions) and switch on Developer mode.
  3. Click Load unpacked and choose the unzipped folder. Pin NomadSF to the toolbar if you like.
Store listings for the Chrome Web Store and Edge Add-ons are on the way; until then, updating means loading the new zip the same way (and clicking Reload on the extension).

VS Code

  1. Download nomadsf-vscode.vsix.
  2. VS Code → Extensions → … → Install from VSIX…
  3. Open a Salesforce DX project and click NomadSF in the status bar. The VS Code extension uses the Salesforce CLI's logins, so it needs the CLI and the plugin.

First steps

  1. Log in to Salesforce in the same browser as usual. NomadSF uses that login (the session cookie of the org), like Salesforce Inspector does; it stores no password or token.
  2. Open the Studio from any Salesforce page: click the NomadSF icon, or the small N tab on the right edge of the page (Alt+Shift+N). It opens for the org of that page.
  3. Settings → Org lists every org you are logged in to in this browser; switch between them there or in the header. Log in to another org in a new tab and it appears when you come back.
  4. Settings → Project (optional): choose your Salesforce project — a folder on this computer or a GitHub repository and branch — to compare it with the org and deploy code from it.
  5. Settings → AI (optional): connect your own AI for the ✦ buttons.

Hubs and panes

The sidebar has five hubs and Settings. A hub is a page with its tools as tabs, and opens on the tab you used last.

  • Side by side: drag a hub from the sidebar, or a tab, to the right half of a pane. Up to three panes; drag the divider to resize, ⧉ opens the hub beside, ✕ closes a pane.
  • Quick jump: ⌘/Ctrl + K, type a few letters, Enter (or Shift+Enter to open beside).
  • Results are kept when you switch tabs or hubs or close another pane. ↻ on a pane starts that tab again with a clean page.

Develop

  • Execute Apex: an editor with Apex highlighting and snippets, log levels, run all (⌘+Enter) or the selection, compile errors on the line, the last 20 snippets.
  • Code: open, check and save Apex classes, triggers, Visualforce pages and components, LWC and Aura; create new ones. With a project chosen, every item is tagged same / different / only in org / only in project, with a side-by-side compare and Use project version.
  • Apex tests: run tests, failures with stack traces, and code coverage line by line.
  • Debug Logs: trace flags and logs, and ✦ an explanation of a log with an AI connected.
Salesforce only accepts Apex and Visualforce changes in production through a deployment, so saving them is off for production orgs (developer orgs allow it).

Data

  • Query: SOQL with autocomplete, saved queries and history, a table you can filter by any column, names for Ids, deleted and archived rows, the Tooling API; export with the Bulk API, split into files.
  • Record: every field of a record (click any Id in a table), edited in place.
  • Import / Update / Delete: from a CSV file (with checks for required fields, picklists and read-only fields before anything runs) or from a query, edited in a grid where only changed cells are sent.
  • Lookup: find the Ids for a column of names in a CSV. Field usage: how full every field is, and who can see it.

Data protection

Backup

  1. + New, give it a name and choose the org.
  2. What to back up: objects you pick (tick them, type their names, or ✦ describe them), or all custom / standard / all objects. Per object, a condition (which records) and the fields (all, only these, all except these). Count records shows the size first.
  3. Settings: incremental runs after the first full one, a schedule (daily or weekly), the folder on your computer, files and attachments, and encryption with a passphrase.
  4. Back up now. Each run is a folder with a CSV per object and a manifest. Backups & restore lists the runs and their records.
Scheduled backups run while NomadSF is open in Chrome; a missed one runs when you open it. Encrypted backups can only be read with the passphrase — it cannot be recovered.

Restore

Open a run under Backups & restore, tick the objects and Compare with the org:

  • Changed since the backup: tick values and Put back.
  • Deleted since the backup: tick records and Bring back. Records still in the recycle bin are undeleted with their Id; the others are created again, with the deleted records they point to, their files, and the records that pointed to them re-linked.

Migrate

  1. From an org (or a backup) into another org.
  2. What to copy: tick objects; per object choose All, Related only (children of what you copy) or Only those pointed to. Children… adds an object's child objects in one click, with counts.
  3. Check plan: the load order, records per object, fields missing in the target, masked fields, and a Links between records table that shows every lookup kept or lost — with a fix for each.
  4. Copy (you type the target org name). Running it again updates instead of duplicating; Undo last copy deletes what it created.

Options: mask personal data (on by default from production into a sandbox), copy files and attachments, and Keep the old Ids in the target org — a field NomadSF_Old_Id__c for large copies with the Bulk API, which you can remove afterwards.

Lifecycle

Jobs in steps on one org: Back up, Check (stop above a limit), Archive (into a backup folder, read back, then delete), Anonymize (personal fields in place), Delete. Start from a template (retention, sandbox refresh, backup then archive) or an empty job.

  • Dry run only counts.
  • Run now stops before the first step that changes data and asks for approval, showing what the steps before it found. You can turn approval off per job; then put a Check step first.
  • Every run keeps a report: matched, changed, failed, who approved.

Release

  • Project: your repository's components, manifests, and a compare with the org — check content, restore, delete from the org, or validate and deploy (code deploys straight from the browser).
  • Metadata: every metadata type of the org, build a package, download a zip or package.xml.
  • Org compare: two orgs (sandbox ↔ sandbox or ↔ production), differences and content, then package.xml, destructiveChangesPost.xml and a deployable zip — or validate, deploy and quick deploy on the target.

Org

  • Users & access: users (find, edit, freeze, activate), login history, setup audit trail, permission sets and groups, object / field / system permissions.
  • Limits, Events (platform events and change data capture, subscribe and publish), REST Explorer, and Activity — everything changed from NomadSF.

AI

In Settings → AI, connect your own provider: Anthropic Claude, OpenAI, Gemini, Mistral, Groq, OpenRouter (key or sign-in), GitHub Models, Ollama on your computer, or any OpenAI-format endpoint. The ✦ buttons then write SOQL and Apex, explain debug logs, test failures, responses and code differences, review code, write test classes, and choose objects for backups and migrations.

AI only fills editors or shows text. Nothing runs or saves until you press the usual button. The key stays in the extension's own storage and goes only to the provider you chose.

Safety and privacy

  • Your login, not ours: the extension calls Salesforce with your browser session. It stores no password or token and has no server; nothing is sent anywhere else.
  • Permissions: cookies and access to Salesforce domains only. Access to an AI provider's address is asked when you connect one.
  • Every change asks first: saving code, editing records, deploying, deleting, restoring and copying data ask you to type the org name. Production orgs are shown in red.
  • Your data stays with you: backups go to a folder you choose on your own computer, optionally encrypted.

CLI and local app (for developers and CI)

The same repository ships the sf fm plugin for the Salesforce CLI. It is what pipelines use, and it runs the local app (sf fm dashboard) that the VS Code extension uses. 

sf plugins install https://github.com/faridmasjedi/plugin-fm
sf fm dashboard --open
Command What it does
sf fm build Delta deployment artifacts from Git changes (submodules, bundles, granular labels and sharing rules)
sf fm deploy Validate, deploy and quick deploy, with tests chosen for the change; status and cancel
sf fm pipeline The optional release train: stages, approvals, scripts, deployment waves
sf fm quality Code Analyzer / PMD / ESLint on changed files, SARIF for pull requests
sf fm drift What changed directly in the org compared with the repository
sf fm rollback Back to an earlier successful deployment
sf fm org create A scratch org or sandbox ready in one command
sf fm runbook · sf fm e2e AI runbooks with approval for every change · Playwright scenarios against any org

Questions

The Studio says "Not logged in"

Open the org in a tab and log in, then come back; or choose another org in Settings. Sessions expire like any Salesforce session.

Why is my developer org shown as production?

Salesforce reports Developer Edition orgs as "not a sandbox", so NomadSF applies the production safeguards. Apex saves still work there.

Does it work without the Salesforce CLI?

Yes — the browser extension needs nothing else. The CLI is only for the sf fm commands, the local app and the VS Code extension.

Where do I report a problem?

GitHub issues. Please leave out org names, record data and session ids.
