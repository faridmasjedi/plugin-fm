NomadSF Guide

NomadSF Studio is a Salesforce workbench in the spirit of the Developer Console and Salesforce Inspector, with data protection tools on top. This guide takes you from installing it to backing up, restoring and moving data.

Install

Chrome or Edge

  1. Download nomadsf-extension.zip from the latest release and unzip it.
  2. Open chrome://extensions (Edge: edge://extensions) and switch on Developer mode.
  3. Click Load unpacked and choose the unzipped folder. Pin NomadSF to the toolbar if you like.
Store listings for the Chrome Web Store and Edge Add-ons are on the way; until then, updating means loading the new zip the same way (and clicking Reload on the extension).

VS Code

  1. Download nomadsf-vscode.vsix.
  2. VS Code → Extensions → … → Install from VSIX…
  3. Click NomadSF in the status bar. The Studio ships with the extension and needs nothing else: it uses the orgs you logged in to with the Salesforce CLI, and NomadSF: Log in to an org logs in to a new one in your browser. Neither the Salesforce CLI nor any local app is needed.

First steps

  1. Log in to Salesforce in the same browser as usual. NomadSF uses that login (the session cookie of the org), like Salesforce Inspector does; it stores no password or token.
  2. Open the Studio from any Salesforce page: click the NomadSF icon, or the small N tab on the right edge of the page (Alt+Shift+N). It opens for the org of that page.
  3. Settings → Org lists every org you are logged in to in this browser; switch between them there or in the header. Log in to another org in a new tab and it appears when you come back.
  4. Settings → Project (optional): choose your Salesforce project — a folder on this computer or a GitHub repository and branch — to compare it with the org and deploy code from it.
  5. Settings → AI (optional): connect your own AI for the ✦ buttons.

Hubs and panes

The sidebar has seven hubs and Settings. A hub opens in a pane with its own sidebar of tools on the left; the bar at the top says where you are (Release › Compare & package). A hub opens on the tool you used last. In a narrow pane the tools' sidebar shows icons only.

  • Side by side: drag a hub from the sidebar, or a tool, to the right half of a pane. Up to three panes; drag the divider to resize, ⧉ opens the hub beside, ✕ closes a pane.
  • Quick jump: ⌘/Ctrl + K, type a few letters, Enter (or Shift+Enter to open beside).
  • Results are kept when you switch tools or hubs or close another pane. ↻ on a pane starts that tool again with a clean page.
  • ⤓ on a pane downloads every table on the page as you see it (filters and sorting applied): an Excel workbook with a sheet per table, a zip with a CSV per table, or JSON. The workbook and the zip load back into Import / Update / Delete, Compare with CSV and Migrate.
  • Tables work the same everywhere. Filters opens conditions: choose a column (or Any column), then pick a value from its list or type one; add as many as you need. Tables with tick boxes also filter on Ticked / Not ticked. Long lists of the same thing come in boxes — one per type, object or kind — that you open and close (Open all / Close all). Related tables are tabs of one table, not a stack of tables. Copy, CSV and JSON take the rows as shown.

Messages and the Log

What a tool is doing, where you are looking — and every message in one place.

  • A message shows next to the button you pressed, drawn by what it is: working (with a spinner), done (green ✓), a problem (red) or a warning (amber).
  • The Log at the bottom of the Studio keeps every message of every tab, newest first, with the time, the tab and the org. Closed, it shows the last message and a count; it opens by itself on a problem. Copy it for a ticket; Clear it when you like.
  • The progress of one job updates one line of the Log instead of filling it.
  • The spinner next to the org at the top shows that NomadSF is waiting for Salesforce; it stops when every answer is in.

Develop

Code

Open, edit and save Apex, triggers, Visualforce, LWC and Aura; see what a class uses and what uses it.

Can change the org — asks for its name first

Open, edit and save Apex classes, triggers, Visualforce pages and components, LWC and Aura — and compare them with your project.

  1. Pick the kind (Classes, Triggers, VF pages…) and a component from the list, or New ….
  2. Compile only compiles it in the org to find errors without saving. Save saves it (you type the org name first).
  3. With a project chosen (Settings › Project), each item is tagged same / different / only in org / only in project. Compare content checks every file; the Compare tab shows both side by side, and Use project version loads it into the editor.
Salesforce only accepts Apex and Visualforce changes in production through a deployment, so Save is off there (developer orgs allow it). Compile only still works.

Dependencies (next to Explain when a class, trigger or component is open): one table with two tabs, Uses and Used by, grouped by type — classes, triggers, pages, flows, objects and fields (a field shows its object). With a project chosen, the project's own references are added. Export it with CSV.

Other metadata: any other type — FlexiPages, flows, permission sets, layouts, custom metadata, labels… Type the type (the list suggests as you type) and pick a component; its tabs are Org, Project, Compare and Dependencies.

  1. Change a file in the editor. A note says it is edited here only — the org's file is not changed yet.
  2. Save … edited file(s) opens the Validate and deploy panel: validate first if you like, then deploy. Saving is the deploy; the page then says ✅ Saved (or ✓ Validated — nothing is saved yet, or ❌ Not saved). Undo drops your edits.
  3. Deploy from project… sends the project's version instead.

✦ Describe a new … (with AI): write a new component of the chosen type from a sentence. You read and change its files, then Create / deploy… validates or deploys it. ✦ Change it changes the open component the same way.

Good to know

  • Compile only is always safe: it finds errors without saving anything.
  • Dependencies comes from Salesforce’s own dependency tracking: classes, triggers, pages, flows, objects and fields. A class named in a string (dynamic Apex) is not found — search the code for it too.
  • Before you change a class, open Dependencies to see which classes and triggers use it, then run their tests in Apex tests. See the scenario Change a class safely.

Execute Apex

Run anonymous Apex in the org, like the Developer Console’s Execute Anonymous window.

Can change the org — asks for its name first

Run anonymous Apex in the org, like the Developer Console's Execute Anonymous window.

  1. Write or paste Apex. Snippets and highlighting help; History… brings back your last 20.
  2. Choose log levels, then Execute (⌘/Ctrl+Enter), or run only the selection (⌘/Ctrl+Shift+Enter).
  3. Read the result: success or the exception, compile errors marked on the line, and the debug log.

✦ With an AI connected, describe what you need ("deactivate users who have not logged in for 90 days").

In a production org you confirm before it runs: anonymous Apex can change data.

Good to know

  • It runs as your user in the org chosen at the top, and asks first every time (in production with a warning): anonymous Apex can change data.
  • Compile errors are marked on their line; the debug log under the result has everything the code logged.
  • Keep long-running work out of it: anonymous Apex has the normal governor limits (use a batch job instead).

Apex tests

Run Apex tests and see the code coverage of every class.

Can change the org — asks for its name first

Select test classes and Run, or Run all local tests. Failures show the message and stack trace. The Coverage tab lists every class; click one to see covered (green) and uncovered (red) lines.

Good to know

  • Tests run in the org (Salesforce runs them, not your computer); a big run can take minutes. You can switch tabs meanwhile.
  • Coverage is from the last runs in the org: run the tests again to refresh it.
  • To find which tests to run for a change, start from Code › Dependencies.

Debug logs

Capture debug logs of what you do in the org, then read them.

Can change the org — asks for its name first

Turn logging on for yourself (a trace flag for a while), do something in the org, then open the new log. The log shows its debug lines, events and limits, and the raw text; ✦ explains it with an AI connected.

Good to know

  • On 30 min / On 1 h adds a trace flag for your user (it asks first); it ends by itself.
  • Only mine hides other people’s logs; Auto-refresh lists new ones as they come.
  • Delete listed removes the logs in the list from the org (it asks first). Salesforce also deletes old logs by itself.

Jobs

Scheduled and background jobs of the org: what runs when, and what is running now.

Can change the org — asks for its name first

Scheduled: every scheduled job (scheduled Apex, report runs, dashboard refreshes, scheduled flows…) with its next and last run and cron expression. Background Apex: batch, queueable and future jobs of the last days with progress, errors and status. Tick jobs and Stop them — you type the org name first.

Good to know

  • Stopping a scheduled job deletes the schedule: it no longer runs until someone schedules it again.
  • Background Apex covers the last days only, as Salesforce keeps it.

Automation

What runs when a record of an object is saved, in Salesforce’s order.

Reads only

Choose an object and see what runs when a record is saved, in Salesforce's order of execution, as a timeline: system validation, before save (before-save flows, before triggers, validation and duplicate rules), saved, after save (after triggers, assignment and workflow rules, after-save flows) and commit. Each card says which events it runs on (insert, update, delete) and whether it is active; a step with many shows the first six and Show all.

  • Filter by kind (triggers, flows, validation rules…), by name, or Active only.
  • Table lists the same as rows, to sort, filter or export.

Good to know

  • Use it when a save fails or a field changes by itself: the rule or flow doing it is on this list.
  • Escalation and auto-response rules cannot be read with the API; the page says when they also apply.
  • Then turn on Debug logs and save the record again to see each one run.

Events

Listen to platform events and change data capture, and publish a platform event.

Can change the org — asks for its name first

Subscribe to a platform event or change data capture channel — new events only, or replay the last 72 hours — and click an event for its payload. Publish a platform event (you type the org name).

Good to know

  • Listening reads only; Publish sends a real event that subscribers act on (it asks first).
  • Replay the last 72 hours to see events sent before you started listening.

REST Explorer

Any REST API call, with the answer, its status and headers.

Can change the org — asks for its name first

Any REST call: method, path, body, the answer with its status and headers. Calls other than GET ask first. ✦ describe the call in plain English.

Good to know

  • GET only reads. POST, PATCH, PUT and DELETE change the org and ask first.
  • Paths start at /services/data/vXX.X/; the version is filled in for you.

Data

Query

SOQL with autocomplete, a filterable table, saved queries and history.

Reads only

  1. Write SOQL with autocomplete for objects and fields (type Account. for the fields of the Account a record points to, as deep as you like), or ✦ ask in plain English.
  2. Options: Names for Ids (adds a column with the name next to every Id), Deleted & archived, the Tooling API.
  3. Run (⌘/Ctrl+Enter). Filter any column, sort, and copy, or download CSV / JSON (CSV opens in Excel as is). Export CSV uses the Bulk API for large results, split into files.
  4. Ids: click to select, ⧉ copies, ↗ opens it in Salesforce, ⓘ shows all its fields.
  5. Related fields…: for an Id column (Case.AccountId, UserLogin.UserId), tick fields of the record it points to (Account Industry, User Email, Profile name); they show next to the Id and are kept for every query with those Ids. When SOQL can follow the link, Add to the query instead puts them in the SELECT.

Plan shows how Salesforce would run the query — with an index or a full scan, and its relative cost (above 1 is slow) — without running it.

Saved queries: name a query and Save query; pick it again from Saved…. Download file / Load file… move them as nomadsf-queries.json, and Load from project reads that file from your project, so a team shares queries through git.

Good to know

  • The table shows up to 2,000 rows at a time; Export CSV uses the Bulk API for any size.
  • Names for Ids and Related fields… add names next to Ids even where SOQL cannot follow the link.
  • ⤓ (top right) downloads every table on the page as an Excel workbook, a zip of CSVs or JSON.

Record

Every field of one record, its history, and what is around it — to edit, or to copy into another org.

Can change the org — asks for its name first

Paste a record Id, a record URL or a username and Show all data: every field with its label, API name, type and value. Edit changes fields in place (you type the org name to save); lookups open the record they point to. For users, Log in as. The History tab lists the record's tracked field changes — when, which field, from, to and by whom — for objects with field history tracking on.

Related: the record and what points to it as a tree (an Account's Contacts, Cases…, and ▸ what points to those). Tick what you want: a relationship takes all its records, ▸ opens it to pick some; Query opens them in Query. Choose an org and Copy: exactly the ticked records are created there, the links between them kept, and Undo this copy deletes them again. Save as Excel keeps them; Open a saved copy… (next to New…) copies them into any org later. On a user, the tree is their access: the ticked permission sets, groups and licenses go with them (the user is created if missing, and so are missing permission sets and groups).

Me opens your own user; a user's name finds them too. New… creates a record of any object: required fields first, picklists as lists, lookups found by name.

Good to know

  • Related counts what points to the record when you open it (system relationships such as history and sharing are left out).
  • A copy creates exactly what is ticked; lookups to records that are not copied are left empty, owners are matched by username.
  • Lookups in Edit and New…: type part of a name, or List to choose from every record of that object (business hours, queues…).
  • New… and Open a saved copy… start clean: the record that was open is put away.

Import / Update / Delete

Insert, update, upsert or delete records from a CSV, an Excel workbook or a zip, with the Bulk API.

Can change the org — asks for its name first

  1. Choose the object and the operation: Insert, Update, Upsert (matched on Id or an External ID field), Delete or Hard delete.
  2. Choose a CSV, an Excel workbook or a ⤓ zip. A workbook with several sheets shows a Sheet picker, and the object follows the sheet’s name. Click a cell to change it before running.
  3. Read the checks: every column is ticked if Salesforce will accept it for this operation, with the reason when not. Ids that are not records of this org, and lookups to records that are not here, are named before anything is sent.
  4. Run (it asks for the org name). The summary counts what succeeded and failed; each failure has its code, message and What it means. Download the successful rows and the failures as CSV.

Delete records matching a query: count what a query returns, then delete it. And edit query results in a grid: query records, change cells, and only the changed cells are sent.

Good to know

  • Before anything is sent, every column is checked: fields that cannot be set are unticked, and related-record columns must use a field Salesforce can find records by (Owner.Username, not Owner.Name).
  • Ids from another org are flagged before you run: an Id belongs to one org, so update or upsert by Id only finds records of this org. To copy records between orgs use Record › Related or Migrate.
  • Upsert matches on Id or a field marked External ID. When the object has none, Migrate’s “Keep the old Ids” adds one (NomadSF_Old_Id__c).
  • Failures come back with What it means in plain words (duplicates, required fields, locked records…), on screen and in the Failures CSV.

Compare with CSV

A spreadsheet of records next to the org: what is the same, what differs, what is missing — then make the org match.

Can change the org — asks for its name first

A CSV of records — from an old org, a backup or a spreadsheet — next to this org. Choose the file, the object and a field to match records by (Email, an External ID…; Ids from another org do not match), and Compare: each row is the same, different (field by field, org now → CSV) or only in CSV. Lookups are compared by name when the CSV has it (Account.Name for AccountId). Edit the CSV changes rows first; Make the org match the CSV updates what differs and inserts what is missing (you type the org name).

Good to know

  • Match on a field both sides share (Email, an External ID, a name): Ids from another org never match.
  • Nothing changes until Make the org match the CSV, which asks first and lists every row that failed.

Lookup

A VLOOKUP against Salesforce: your file back with the Ids or fields you need.

Reads only

A VLOOKUP against Salesforce: choose a CSV, the column to look up, what it holds (Ids of an object, or values of a field), and the fields to bring back. You get your file back with new columns — Column → Found and Column → Field — and a list of the records found. Columns your file already has (from an export with names for Ids) get (lookup) added.

Good to know

  • Use it to turn names into Ids before a load (Account names → AccountId), or to add fields to an export.
  • Values that match several records are shown as such; nothing is guessed.

Schema

Everything about an object: fields, relationships and record types.

Reads only

Everything about an object: its fields (type, length, required, unique, external Id, formula, help text, picklist values — click a field), its relationships (a diagram of what it points to and what points to it; click an object to open it; system objects hidden unless you ask) and its record types.

Good to know

  • Click a field for its picklist values, formula, help text, length and whether it is required, unique or an External ID.
  • The relationships diagram is clickable: open the object a lookup points to.

Field usage

How full each field of an object is, where it is used and who can see it.

Reads only

For an object: how full every field is (records with a value), where it is used (references, for custom fields), and which profiles, permission sets and groups can read or edit it.

Good to know

  • Count all runs one query per field: on a big object, count only the fields you need.
  • A field nobody fills and nothing uses is a candidate for clean-up; check Dependencies first.

Release

Validate and deploy — the same everywhere

Every place that builds a package ends with the same panel: Project, Compare & package, Metadata, Org compare, Code and the AI drafts.

Can change the org — asks for its name first

  • Choose what goes in: rows come in a box per metadata type. Each row has its own choice — to package (package.xml) or destructive (destructiveChanges.xml) — and each box has + All to package, − All destructive and Clear.
  • What's in the package lists it file by file (A added, M changed, D deleted); click a file to see its code.
  • Into: the org it goes to. Tests: no tests (not in production), these test classes, all local tests, or all in the org. Find dependent tests names the test classes that reach the classes and triggers of the package — add or remove any. Deletions run after the deploy, or before it.
  • Validate on … checks it without changing the org; Deploy to … deploys it. After a successful validation, Quick deploy deploys it without running the tests again. Component errors and test failures show as tabs; the result goes to the Log too. Deployable zip downloads the package for your pipeline.

Good to know

  • Source-format files (a project or a branch) are converted to what the Metadata API expects — objects with their fields, custom labels one by one, and so on. Anything that cannot be converted yet is named above the buttons and left out.
  • Every validate and deploy asks you to type the org's name first.

Project

Your Salesforce project next to the org: what differs, bring org changes in, deploy project changes out.

Can change the org — asks for its name first

Your Salesforce project (a folder on this computer or a GitHub repository, chosen in Settings › Project) against the org. Use it to see what differs, bring org changes into the project, or deploy project changes to the org.

  1. Overview: the project's components in a box per type (Open in Metadata on each), and its manifests (package.xml files).
  2. Compare with the org: choose the metadata types (or All), then Compare. The tiles count in both, only in org and only in project — click one to show just those. Compare content checks the files of components in both (same / different).
  3. Choose per row or per type: to package deploys the project's version, destructive deletes it from the org. Add all differences takes everything that differs. A .forceignore path leaves files out.
  4. Then What's in the package and Validate and deploy. In the CLI app, Restore into project also retrieves the ones only in the org into your folder.

Good to know

  • Choose the project once in Settings; every page uses it.
  • Deploys and deletes ask first; a validation never changes the org.

Compare & package

What one branch brings into another — like a pull request — as package.xml and destructiveChanges.xml; or a branch against an org, a manifest, two orgs.

Can change the org — asks for its name first

Open the project folder (the repository with sfdx-project.json): Compare & package reads its git history, branches and tags, and writes nothing to it.

  1. Branch ↔ Branch: Source is the branch with the changes, Target where they go (⇄ swaps them). Like a pull request takes only what Source added since it branched from Target; Everything that differs compares the two as they are now.
  2. Compare: the package by type — added, changed, deleted — with a choice per row and per type. Renamed files are a new component plus the old one deleted (keep the old one if you like). Custom labels are counted one by one.
  3. Files lists every file under Changed / added and Deleted (and what the .forceignore left out). Click one to see the difference, and ✦ Explain the difference with AI.
  4. Download the Manifest (zip) or the manifest with the changed files, or validate and deploy it.

The other ways to compare, from the switch at the top:

  • From a manifest: a package.xml (and optional destructiveChanges.xml) with the files of a branch, checked against an org — what is the same, different, missing.
  • Branch ↔ Org: every type of a branch against the org at the top, then deploy what differs.
  • Org ↔ Org: Org compare, here too.

Good to know

  • A GitHub project is read without its history, so it cannot be compared here; open the folder instead.
  • Find dependent tests follows the classes and triggers of the package to the test classes that call them — in the branch, not only in the org.

Metadata

Build a package (or a delete package) from any metadata of the org.

Can change the org — asks for its name first

Build a package by hand from any metadata type of the org.

  1. Choose a type, tick components, Add to package — a package can mix types. The package is listed in a box per type (click a row to remove it), then What's in the package, where a click shows the component itself (its XML or code).
  2. Download zip retrieves them; package.xml / Copy package.xml give the manifest; Retrieve into project in the CLI app.
  3. To remove things from the org: tick them and Add to delete. Choose destructiveChanges.xml, destructiveChangesPre.xml (deleted before the deploy) or destructiveChangesPost.xml (after), then download it, copy it, or Manifests (zip) for both files. The page shows the sf project deploy start command to use.

Good to know

  • Deploy the package to another org with Validate and deploy under it — choose the org in Into — or download it for your pipeline.

Deployments

The org’s deployments and validations, their failures, and quick deploy.

Can change the org — asks for its name first

The org's deployments and validations — who, when, components and tests, how many failed. Click one for its component and test failures. A validation that succeeded with tests in the last 10 days can be Quick deployed from here (you type the org name).

Good to know

  • Quick deploy works for a validation that ran tests and succeeded in the last 10 days, with no change in the org since.

Access

Users

A user and everything they have: details, permission sets, permissions, groups, licenses, apps and logins.

Can change the org — asks for its name first

Find a user by name, username, email or Id. Details edits any field; Freeze, Deactivate, Log in as. Beside it: their Permission sets & groups, System permissions (every permission they have, and the profile, permission set or group that gives it), Groups & queues (public groups, queues, personal groups), Licenses, OAuth apps and Login history.

Change them right there: Remove a permission set, group, membership or license, or Add one from the list under it (you type the org name each time). In Details › Edit, lookup fields such as ProfileId, UserRoleId or ManagerId have a Find … by name box: choose one and its Id is filled in.

Snapshot: Save snapshot (CSV) keeps everything about a user in one file — fields, profile, role and manager (by name), permission sets and groups, licenses, public groups and queues, and the connected apps they sign in to (those are to check only: the user connects an app themselves). In any org (a new sandbox, say), Compare … with a snapshot… finds the same user (username, with or without a sandbox suffix) and lists every difference; tick what to change and Make the user match the snapshot. You can edit the CSV in Excel first. When the user is not in that org, Create the user… makes them under a new username (usernames are unique across every org), with the same fields, profile, role, manager and access; no welcome e-mail is sent.

Everything (workbook) next to a user saves every tab — details, permission sets and groups, system permissions, groups and queues, licenses, OAuth apps and login history — a sheet each (⤓ takes only the tab on screen).

Good to know

  • Every add or remove asks for the org name first, and shows straight away.
  • Everything (workbook) saves every tab of the user, a sheet each — ⤓ takes only the tab on screen.
  • Snapshot compare says up front which permission sets, groups and licenses the org lacks; when the snapshot’s org is connected, Create them from … copies them over first.
  • To copy a user and only some of their access to another org, use Record › Related on the user.

Permission sets & groups

Permission sets and permission set groups: who has one, assign or remove it, create one.

Can change the org — asks for its name first

One table, with a box for Permission set and one for Permission set group (filter it, or export it as CSV). Click a row: its Assigned tab lists who has it — tick users and Remove selected… — and Assign to users finds users by name, username, profile, role or public group, with an optional expiry. You type the org name first.

+ New permission set or group, in its own box at the top, creates one (label and API name), ready for Permissions.

Good to know

  • Assign by usernames, a profile, a role or a public group, with an expiry date if you like.
  • A permission set group’s permissions come from its permission sets: change them in Permissions.

Permissions

What a profile, permission set or group allows — and change it.

Can change the org — asks for its name first

What a profile, permission set or group allows — object access, field access, user & system permissions, or All together.

Changing permissions:

  1. Choose a custom permission set or custom profile and Edit… (standard profiles cannot be changed).
  2. Tick or untick object access, field access and user & system permissions; add an object, or choose one under Field access for all its fields. What Salesforce requires is kept: Edit needs Read, Modify all needs everything. Changed boxes are outlined; nothing is sent yet. (Edit… is off, with the reason, when your user can't change permissions in this org.)
  3. Save — you type the org name; anything that fails is listed, the rest is saved.

A permission set group gets its permissions from its permission sets: choose the group to add or remove permission sets, and Salesforce recalculates it.

Apps, classes & more: the Apex classes, Visualforce pages, custom permissions, connected apps (pre-authorized OAuth access) and apps (App Launcher) a permission set or custom profile gives access to — add and remove them. Record types: which ones it may use (and, for a profile, each object's default). Page layouts (profiles): the layout for each object and record type. Tabs (permission sets): Visible, Available or Hidden. Login IP ranges (any profile, standard ones too). Record types, layouts and login settings are deployed with the Metadata API: only those settings change.

Field access while editing: choose an object to list every field that can have field permissions, with Read and Edit (and All Read / All Edit). Required and system fields are not listed: everyone with the object can use them.

Clone… copies a profile (to a new custom profile with the same license), a permission set or a permission set group under a new name; nobody is assigned.

Good to know

  • Standard profiles cannot be edited (only their login IP ranges); clone one first.
  • Changes are only sent on Save, which asks first and lists anything that failed.

Custom permissions

Custom permissions: who gives each one, grant it, create a new one.

Can change the org — asks for its name first

Every custom permission and the permission sets, profiles and groups that give it; grant it to another permission set or profile, or remove a grant. New custom permission… creates one (Metadata API) and grants it at once to the permission sets and profiles you tick.

Groups & queues

Public groups and queues with their members; add or remove members.

Can change the org — asks for its name first

Every public group and queue, with its members (users, roles, roles and subordinates, other groups) and the objects a queue can own. Choose one to add members (first choose what: a user, a public group, a role or a role and its subordinates) or remove them.

Assigned users

Data protection

Backup

Back up records to a folder on your computer, now or on a schedule; restore them later.

Can change the org — asks for its name first

  1. + New, give it a name and choose the org.
  2. What to back up: objects you pick (tick them, type their names, or ✦ describe them), or all custom / standard / all objects. Per object, a condition (which records) and the fields (all, only these, all except these). Count records shows the size first.
  3. Settings: incremental runs after the first full one, a schedule (daily, weekly, or every N hours, days, weeks or months), the folder on your computer, files and attachments, and encryption with a passphrase.
  4. Back up now. Each run is a folder with a CSV per object and a manifest; Download as zip works without a folder. Backups & restore lists the runs.
Scheduled backups run while NomadSF is open; a missed one runs once when you open it. Encrypted backups can only be read with the passphrase — it cannot be recovered. In VS Code the folder is chosen with VS Code's folder picker.

Good to know

  • Backups only read the org. Restoring writes, and asks first.
  • An encrypted backup can only be read with its passphrase: it cannot be recovered.

Restore

Put back changed values and bring back deleted records from a backup run.

Can change the org — asks for its name first

Open a run under Backups & restore, tick the objects and Compare with the org:

  • Changed since the backup: tick values and Put back.
  • Deleted since the backup: tick records and Bring back. Records still in the recycle bin are undeleted with their Id; the others are created again, with the deleted records they point to, their files, and the records that pointed to them re-linked.

Lifecycle

Jobs in steps: back up, check, archive, anonymize, delete — on a schedule.

Can change the org — asks for its name first

Jobs in steps on one org: Back up, Check (stop above a limit), Archive (into a backup folder, read back, then delete), Anonymize (personal fields in place), Delete. Start from a template (retention, sandbox refresh, backup then archive) or an empty job, and schedule it like a backup.

  • Dry run only counts.
  • Run now stops before the first step that changes data and asks for approval, showing what the steps before it found. You can turn approval off per job; then put a Check step first.
  • Every run keeps a report: matched, changed, failed, who approved.

Good to know

  • Start with Dry run: it only counts.

Org to org

Two orgs, A → B

The two orgs every Org to org tool works on: A (from) and B (into).

Reads only

The tools that work on two orgs share one pair, chosen in the bar at the top of each: A (compare from, copy from) and B (compare with, copy and deploy into). ⇄ swaps them. The pair is remembered, and A starts as the org chosen at the top of the Studio. Anything written goes into B, and you type B's name first.

Under the bar: what your user may do in each org — full, read only (can read setup, can't change permissions) or limited (can't read profiles, permissions or code) — and which permission is missing. What one org could not be read shows as ? ("not read in B"), never as a difference; copying into B is turned off when your user there can't change permissions.

Migrate

Copy records from an org, a backup or a workbook into another org, keeping every link between them.

Can change the org — asks for its name first

Copies records from one org (or a backup) into another and keeps every link between them: a Contact still points to its Account, a Case to its Contact, and so on — even though every record gets a new Id in the target.

  1. From: org A of the bar, a backup run, or Files — an Excel workbook, a CSV or a ⤓ zip: match each sheet to an object of B (sheets named after an object are matched already) and Use these files; lookup columns holding Ids of other sheets are pointed to the new records. Into: org B. Choose them in the bar at the top (the same two orgs for every tool of the hub).
  2. What to copy: tick objects. Per object: All records (or a condition), Related only (only the children of what you copy — e.g. the Contacts of the Accounts you copy), or Only those pointed to (e.g. only the Users your records point to). Children… adds an object's child objects in one click, with counts.
  3. The Plan table shows it all at once, each object under the one it links to (Contacts under Accounts, via AccountId): which records, a SOQL condition, a limit (the newest N records), the fields (all, only some, or all except some). From each row: + Children…, + Parent… (also copy the records its lookups point to) or Remove. A related object follows the lookup it was added through (via AccountId → Account): only the Contacts of the copied Accounts come along, not every Contact owned by a copied User. Change it in the row, or choose via any lookup to the objects above.
  4. Check plan before anything is written. It shows the load order (parents before children), records per object, fields missing in the target, masked fields, and Links between records: every lookup, whether it is kept or lost, and a fix for each lost one (add the object, or match on a field such as Name or an external Id).
  5. Copy — you type the target org name. Progress shows per object; failures are listed with a CSV.
  • Again: running the same copy again updates the records it created instead of duplicating them. Undo last copy deletes what the last copy created.
  • Mask personal data: names, emails and phones are replaced (on by default from production into a sandbox).
  • Files and attachments can be copied with their records.
  • Keep the old Ids in the target org: for large copies with the Bulk API, a field NomadSF_Old_Id__c remembers each source Id; remove it afterwards with one click.

Good to know

  • Check plan reads only; nothing is written until Copy, which asks for B’s name.
  • From files: open ▸ on a sheet to tick only the rows you want; press Use these files again after changing the ticks.
  • An object set to Related to the ones above takes only the records whose parent is copied; set it to All to copy it on its own.
  • For one record and what hangs under it, Record › Related is quicker.

Org compare

Metadata of A and B side by side; build a package of the difference and deploy it into B.

Can change the org — asks for its name first

A (the source) and B (the target) side by side — sandbox ↔ sandbox, or ↔ production: choose the metadata types (Common picks the usual ones) and Compare. The tiles count what is only in source, only in target and in both — click one to show just those. Compare content of those in both splits them into different and same.

  1. The components come in a box per type, with what each holds (2 only in source, 1 different…). Open a box and choose per row — Add to package (from A) or Destructive change (delete from B) — or for the whole type with + All to package / − All destructive. Add all differences takes everything only in A or different.
  2. What's in the package lists every file; click one to see A and B side by side.
  3. Validate and deploy into B — Find dependent tests, validate, then deploy or quick deploy. You type B's name; a production B is shown in red. Or download the package.

Access

Users and permissions in two orgs: find, compare, copy access from A into B.

Can change the org — asks for its name first

  • Find a user: a name, username, email or Id — is that user in A, in B, or both? Usernames, active, profile and last login side by side. The same user is matched by username, with or without a sandbox suffix (ann@acme.com ↔ ann@acme.com.uat ↔ ann@acme.com.dev), else by name. Click a user to compare them in full (or click one of A and one of B).
  • Compare: two users in full (B is found by username — details, everything assigned and its access, permissions, last logins), two profiles, permission sets or permission set groups (B with the same name or API name is chosen for you), or Everything: every profile, permission set and group of both orgs — only in A, only in B, different (how many system permissions and objects), or the same; click one for the details. Permissions one org does not have at all (licenses, features) are left out.
  • Copy A's access into B: comparing two permission sets or profiles, tick differences and copy them — system permissions, object and field access — into B (you type B's name).
  • Assigned users: the users of a permission set, group, license, profile, role or queue in both orgs — in both, only in A, only in B.

Connected apps

Connected apps in two orgs, and the people who use them in each.

Reads only

Connected apps, external client apps and apps used through OAuth in A and B: which are only in one org, and for apps in both, their settings (admin-approved users, refresh-token and session policies, start URL…) and the profiles and permission sets that may use them. Click an app for the people who use it in A and in B (matched by username); click someone in both to compare the two users in full.

Seed a sandbox with one customer

A tester needs one real-looking Account with its Contacts and Cases in a sandbox — without copying all your data.

  1. In production, open the Account in Data › Record and choose Related.
  2. Tick Contacts and Cases (all of them), or press ▸ to tick only some.
  3. Choose the sandbox under Copy into, keep Mask personal data on, press Copy and type the sandbox’s name.
  4. Check the records in the sandbox. Wrong choice? Undo this copy deletes exactly what was created.
For many Accounts at once (the newest 100, with their Contacts), use Org to org › Migrate with a limit and Related to the ones above.

Give a new starter the same access as a colleague

A new person joins a team and needs what their colleague has — no more.

  1. Access › Compare: Two users, the colleague and the new starter. The differences are listed per tab.
  2. In Access › Users, open the new starter and add the missing permission sets, groups and queues (each asks for the org name).
  3. Compare again: it should only show what is personal (name, e-mail, logins).
To give the same access in another org, open the colleague in Record › Related, tick their permission sets and groups, and copy into that org (the user is created there if missing).

Set up a user in a fresh sandbox exactly as in production

After a sandbox refresh, a tester must have the same profile, role and access as in production.

  1. In production, Access › Users: find the user and Save snapshot (CSV).
  2. Switch to the sandbox. With no user chosen, Compare a snapshot with this org… and pick the file.
  3. If it lists permission sets or licenses the sandbox lacks, press Create them from production (or deploy them first).
  4. If the user is not there, Create the user… with a new username; otherwise tick the differences and Make the user match the snapshot.
No welcome e-mail is sent to users created this way.

Fix a data load that failed

You imported 2,000 Contacts and 140 failed.

  1. In Import / Update / Delete, read What it means next to each failure (or open the Failures CSV — it has the same columns).
  2. Missing or wrong lookups? Use Lookup on the failures file to turn Account names into AccountId.
  3. Duplicates? Update the existing records instead: Upsert on an External ID, or turn the duplicate rule off for the load.
  4. Load only the fixed rows again; the summary shows what succeeded.

Update the org from a spreadsheet someone sent you

A colleague sends a spreadsheet of Accounts with corrected phone numbers and industries.

  1. Data › Compare with CSV: choose the file and the object, and match on a field both sides share (an External ID, or the name).
  2. Read the differences field by field: org now → spreadsheet.
  3. Untick rows you don’t want, then Make the org match the CSV (it asks first).
Never match on Ids from another org: an Id belongs to one org.

Find who can see a sensitive field

Security asks who can read the Salary field on Contact.

  1. Access › Object access: choose Contact and the Salary field, Show who. Each user is listed with what gives them access.
  2. Access › Overview: filter View All Data and Modify All Data — those users see every field too.
  3. Remove access where it should not be, in Permissions (Edit… › Field access).
  4. Org › Org health lists everyone with powerful permissions, to review regularly.

Change a class safely

You need to change an Apex class and want to know what else to test.

  1. Develop › Code: open the class and press Dependencies: Used by lists the classes, triggers, pages and flows that use it.
  2. Make the change and Compile only to find errors without saving.
  3. Apex tests: tick the test classes of what uses it (and the class’s own), and Run. Check the coverage.
  4. Deploy it: from your project (Release › Project) or from a sandbox with Org compare.

Move changes from a sandbox to production

A feature is finished in a sandbox and must go to production.

  1. Org to org › Org compare: A = the sandbox, B = production. Choose the types and Compare.
  2. Tick what belongs to the feature (Select the difference ticks all of it), then Build package.
  3. Validate it into B with the test level you need — production is shown in red and asks for its name.
  4. Later, Quick deploy the validation from Release › Deployments.

Find out why saving a record fails

Users report “an error occurred” when they save a Case.

  1. Develop › Automation: choose Case — every validation rule, flow and trigger that runs on save, in order, with its message.
  2. Debug logs: On 30 min, save the Case again, open the new log (✦ explains it).
  3. Record › History shows what changed on the record and who changed it.

Free up storage safely

The org is close to its data storage limit.

  1. Org › Limits › Storage: the objects using the most, with an estimate of their size.
  2. Back up what you will delete with Backup (a condition such as CreatedDate < LAST_N_YEARS:3).
  3. Delete by date from Storage, or set up a Lifecycle job (archive, then delete) and run it as a Dry run first.

Settings

Three tools in the Settings sidebar: Orgs, AI and Project.

  • Orgs: the orgs you are logged in to.
  • AI (browser extension): your own provider for the ✦ buttons — in the CLI app it is on the app's AI page.
  • Project: a folder on this computer or a GitHub repository and branch. Every page uses it; Compare & package needs the folder, as it reads the project's git history.

AI

In Settings → AI, connect your own provider: Anthropic Claude, OpenAI, Gemini, Mistral, Groq, OpenRouter (key or sign-in), GitHub Models, Ollama on your computer, or any OpenAI-format endpoint. The ✦ buttons then:

  • Write: SOQL from a sentence (Query, and the query of Import / Update / Delete), Apex, test classes, and new metadata — a trigger, a Visualforce page, an LWC or Aura bundle, a field, any other type (Code, and Code › Other metadata).
  • Change an open component from a sentence (Code › Other metadata › Change it): the changed files show as unsaved edits to read first.
  • Explain and review: code, debug logs, test failures, responses, differences between two versions. Answers come formatted — headings, lists, tables and code blocks.
  • Choose: objects for backups and migrations, and which CSV column goes to which field on an import.
AI only fills editors or shows text. Nothing runs or saves until you press the usual button — metadata the AI writes goes through the same Validate and deploy panel as everything else. The key stays in the extension's own storage and goes only to the provider you chose.

Safety and privacy

  • Your login, not ours: the extension calls Salesforce with your browser session. It stores no password or token and has no server; nothing is sent anywhere else.
  • Permissions: cookies and access to Salesforce domains only. Access to an AI provider's address is asked when you connect one.
  • Every change asks first, in every org: saving code, editing records, validating and deploying, deleting, restoring and copying data, changing permissions — you type the org name (in Org to org, B's name). Running Apex or tests, turning on debug logs and Log in as ask too. Production orgs are shown in red.
  • Only what your user may do: NomadSF works with your own Salesforce permissions. Each tool says what your user is missing there, and Access › Your access lists it all.
  • Your data stays with you: backups go to a folder you choose on your own computer, optionally encrypted.

Questions

The Studio says "Not logged in"

Open the org in a tab and log in, then come back; or choose another org in Settings. Sessions expire like any Salesforce session.

Why is my developer org shown as production?

Salesforce reports Developer Edition orgs as "not a sandbox", so NomadSF applies the production safeguards. Apex saves still work there.

Does it work without the Salesforce CLI?

Yes — the browser extension and the VS Code extension need nothing else. In VS Code, the orgs you logged in to with the Salesforce CLI show up by themselves (the CLI program itself is not used).

Where do I report a problem?

GitHub issues. Please leave out org names, record data and session ids.
